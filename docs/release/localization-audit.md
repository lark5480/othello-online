# 本地化覆盖审计（lean）

> 范围：`src/` 前端与 `edge-functions/` 后端的**用户可见文案**。
> 方式：只读扫描（`grep` + 逐文件人工核对），**未修改任何源码**。
> 时间：2026-10-12。
> 前提：本项目是**纯中文单语界面**，任务要求只出审计结论与「将来要支持英文时改动面有多大」的评估，**不做 i18n 改造**。

## 0. 结论速览

| 项 | 结论 |
|---|---|
| 是否具备 i18n 能力 | ❌ 无。无框架、无字符串表，文案硬编码在组件里 |
| 文案规模 | 约 **105 处**用户可见文案，分布在 **9 个文件**（去重后约 90 条） |
| `<html lang>` | ✅ 正确（`zh-CN`） |
| 依赖环境的日期/时间格式化 API | ✅ **零使用**（`toLocaleString` / `Intl.*` 全项目零命中） |
| 中英混排 | 🟡 基本自然；发现 **1 类一致性缺陷**：半角/全角逗号混用（3 处半角） |
| emoji 使用 | 🟡 与项目自身约定冲突（`AGENTS.md` 说不用 emoji，主题切换用了 `☀️ 🌙`） |
| 是否建议现在做 i18n | ❌ 不建议。且将来若要做，**改动面中低** |
| 本轮是否需要修 | ❌ 不需要（发现项均为低危观感问题，非功能缺陷） |

## 2. 中英混排检查

### 2.1 自然、可接受的部分

- `Othello Online`（首页大标题，英文）+ `黑白棋 · 在线对战`（副标题，中文）：有意为之的品牌处理，读起来自然。
- 技术缩写混排：`AI`、`AI 思考中…`、`Web Audio`、`4 层 Minimax + 剪枝`、`KV`、`6 位房间码` —— 面向技术型使用场景，不影响理解。
- 数字与中文混排：`请输入 6 位房间码`、`{n} 手`、`战绩 · 中等` —— 中文排版惯例正确（中英/数字间留空格）。

### 2.2 发现的问题

**问题 1（一致性缺陷 · 低危）：半角与全角逗号混用**

同一项目内同时存在两种逗号：

| 位置 | 写法 | 标点 |
|---|---|---|
| `src/pages/Home.tsx:30` | `创建房间失败,请稍后重试` | **半角** `,` |
| `src/pages/Home.tsx:59` | `加入失败,请稍后重试` | **半角** `,` |
| `src/utils/api.ts:19` | `在线对战后端存储(KV)尚未配置,暂时无法联机对战。可直接玩「人机对战」,或本地 npm run dev 双人开玩。` | **半角** `,` ×2 + 半角括号 `(KV)` |
| `src/pages/Room.tsx:143` | `落子失败，请重试` | 全角 `，` |
| `src/components/MoveHistory.tsx:39` | `对局开始后显示每一步坐标，点击可回顾该手棋形。` | 全角 `，` |
| `src/pages/AIGame.tsx:31-34` | `随机落子，适合热身` 等 4 条 | 全角 `，` |

→ 中文句子里应统一用全角 `，` 与全角括号 `（KV）`。**这是本次审计发现的唯一一类真实一致性缺陷**，纯观感、不影响功能。共 3 处半角逗号（`Home.tsx` ×2、`api.ts` ×2 个逗号与 1 对括号）。

**问题 2（与项目自身约定冲突 · 低危）：emoji 被用作文案前缀**

`src/components/ThemeToggle.tsx:38` 使用了 `◐ 跟随系统` / `☀️ 亮色` / `🌙 暗色`，其中 `☀️` 与 `🌙` 是 emoji。
而 `AGENTS.md` 的代码约定明确写着「棋子用 CSS 圆形 + 内联 SVG 图标，**不用 emoji 图标**」。

→ 两处影响：(a) 与自身约定不一致（描述与实现不符）；(b) emoji 在不同系统/浏览器上的字形与字宽不一致，会让这个按钮的宽度在 Windows / macOS / Android 间有细微差异。**低危**，但属「跨平台表现」这一类本地化相关问题，一并记录。

**问题 3（面向玩家的文案里混入技术术语 · 低危）**

`src/utils/api.ts:19` 的 `STORAGE_HINT` 是**玩家在联机失败时会读到的提示**，其中包含 `本地 npm run dev 双人开玩`。
→ 对项目的开发者本人没问题，对「被邀请来下棋的朋友」则是无效信息。若这条文案面向普通玩家，建议保留「可直接玩人机对战」，把 `npm run dev` 部分删掉或改为「或与身边人共用一台设备轮流下」。

## 3. `<html lang>` 检查

`index.html:2`：`<html lang="zh-CN">` —— **正确**。

这个属性影响四件事，本项目都在意得上：

1. 屏幕阅读器用哪种语音读页面（本项目有 `aria-label`，无障碍是明确目标之一）；
2. 浏览器「是否提示翻译此页面」的判断（`lang` 对了才不会无缘无故弹翻译条）；
3. 中文字体的选择与回退顺序；
4. CJK 文本的换行与标点挤压规则（`lang="zh"` 才有正确的避头尾处理）。

全项目仅此一处声明，**无遗漏、无错误**。

## 4. 日期 / 时间格式是否依赖环境

**结论：不依赖，这是本地化面上本项目最干净的一块。**

扫描 `src/` 与 `edge-functions/`：

- `toLocaleString` / `toLocaleDateString` / `toLocaleTimeString` / `Intl.*` —— **零命中**。
- 界面上的所有数字都是纯整数（比分、手数、胜/负/和/局、净胜子差），配合 `tabular-nums` 等宽渲染，**不存在区域差异**。

存在 `Date.now()`，但**全部是内部时间戳，不进界面**，与区域格式无关：

| 位置 | 用途 |
|---|---|
| `src/utils/gameLogic.ts:224,242,265,331` | 写入 `createdAt` / `updatedAt`，供乐观并发做数值比对 |
| `src/utils/ai.ts:319` | 本地人机对局的 `updatedAt` |
| `edge-functions/api/room/create.ts:17` | 房间码冲突兜底时的时间戳后缀 |

→ 附带结论：**将来若要做「对局时长」「上一局结束于 …」这类显示，格式化策略需要从零建立**（现在完全没有）。这是未来做 i18n 时唯一需要新增能力的地方。

## 5. 后端错误文案与前端的分层

后端返回**英文机器可读错误码**，前端映射成中文：

| 后端返回 | 前端处理 | 位置 |
|---|---|---|
| `room not found` | → `房间不存在` | `src/pages/Home.tsx:56` |
| `room full` | → `房间已满` | `src/pages/Home.tsx:58` |
| 其它（`invalid body`、`playerId required`、`not your turn`、`state conflict` 等） | → 通用中文兜底（`加入失败,请稍后重试` / `落子失败，请重试` 等） | `Home.tsx` / `Room.tsx` |
| `storage not configured` | → `STORAGE_HINT` 整句 | `src/utils/api.ts:18-23` |

**判定：分层是正确的** —— 后端只给机器可读码，文案由前端负责。这正是未来做多语言时该插入翻译的位置。

唯一注意点：`src/utils/api.ts` 的 `parse()` 在**没有映射**时会原样把后端英文串（或 `HTTP 500`）塞进 `ApiError.message`。逐条核对后，所有面向用户的展示路径都有中文兜底，**当前未见英文漏到界面**，但这是「新增接口时容易漏掉映射」的结构性风险，值得在改动接口时留个心眼。

## 6. 若将来要支持英文：改动面评估

### 6.1 规模与工作量

**结论：中低改动面。** 依据：

| 维度 | 情况 | 对改动面的影响 |
|---|---|---|
| 文案总量 | 约 105 处 / 9 个文件 | ✅ 小 |
| 长文本 | 最长一句是 `STORAGE_HINT`，其余都是短标签与短句 | ✅ 小 |
| 语法复杂度 | 中文 → 英文基本 1:1，无复数、无性数格、无语序重排需求 | ✅ 小 |
| RTL / 双向文本 | 无 | ✅ 无 |
| 图片内含文字 | **无任何位图资产**（棋子/棋盘/图标全是 CSS 与内联 SVG） | ✅ **本地化不需要重做任何美术** |
| 布局风险 | 按钮与说明文字均为自适应宽度；但英文比中文长，短标签在窄屏可能换行 | 🟡 需回看一遍 |
| 模板拼接 | 2 处（见 6.2） | 🟡 需改为参数化 |
| 日期/数字格式化 | 当前完全空白（§4） | 🟡 需从零建策略 |
| 语言声明切换 | 仅 `index.html` 一处 | ✅ 小 |

### 6.2 需要特别注意的两处模板拼接

1. `src/pages/AIGame.tsx:301`：`人机对战 · ${难度} · 你执${黑/白}`
   —— 英文语序不同，不能靠字符串拼接，必须改成带参数的翻译键（如 `t('ai.subtitle', { difficulty, color })`）。
2. `src/components/MoveHistory.tsx:67`：`第 {n} 手 · {坐标}`
   —— 同理，需参数化。

### 6.3 建议的实施路径（若真的要做）

- **第一步（零行为变更、零风险）**：把散落在 9 个文件里的字面量**集中到一个 `src/utils/strings.ts`**（仍是纯中文，暂不引入任何 i18n 运行时）。
  这一步不动 UI、不改逻辑、可被现有测试直接覆盖，收益是「文案从散落变集中」；之后要加语言，只是换数据源，不用再动组件。
- **第二步（真有英文需求时）**：加一个轻量取词函数（如 `t(key, params?)`，约 30 行即可自研）+ 语言切换 + `index.html` 的 `lang` 跟随切换。
- **不建议现在做**：引入 i18next / react-intl 一类运行时。本项目明确的取向是**零运行时依赖**（仅 React / ReactDOM / React Router）与体积预算（首屏约 61 KB brotli）；在没有真实多语言需求前引入翻译框架，是用预算换用不上的能力。

### 6.4 本轮明确不做的事

- 不改任何源码（硬约束）；
- 不做 i18n 改造、不建字符串表；
- §2.2 的标点与 emoji 问题**记录在案即可**，属可随手修的观感项，不与本次发布绑定。
