# 版本号规范（lean）

> 适用范围：`othello-online` 一个小项目、一个版本号、无包发布。
> 目标：让「线上跑的是哪一版」永远可追溯，且不用开会讨论。
> 依据：[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)（链接已核验有效，2026-10-12）。
> 变更记录见仓库根 [`CHANGELOG.md`](../../CHANGELOG.md)。

## 1. 版本号的唯一来源

`package.json` 的 `version` 字段。除此之外任何地方都不要再写版本号。

> 当前界面**不显示版本号**（源码中零引用），所以想确认线上版本只能对着本规范和 CHANGELOG 查。若将来要在页脚显示，需从 `package.json` 注入构建期常量 —— 属新功能，不在本轮范围。

## 2. 格式与含义

`主版本号.次版本号.修订号`（`X.Y.Z`），按语义化版本递增：

| 位 | 什么时候 +1 | 本项目的具体判断标准 |
|---|---|---|
| **主** `X` | 不兼容的改动 | 老客户端配不上新服务端。例：对局数据结构**不兼容**变化（字段改名/删除、类型变了）、接口路径调整、房间码规则变更、已有房间的旧数据在新版本下读不出来。<br>⚠️ 本项目升主版本要格外谨慎，原因见 §4。 |
| **次** `Y` | 向后兼容的新功能 | 新增玩家可见的功能；或对局数据结构**新增**字段（旧的字段还在、旧客户端不会崩）。例：`1.1.0` 给对局状态新增棋谱字段 `moves`，属于此类。 |
| **修订** `Z` | 向后兼容的缺陷修复 | 只修 bug、不改行为契约。例：翻转动画颜色显示错误、文案与错别字、纯文档修正。 |

补充约定：

- 次版本号递增时，修订号归零；主版本号递增时，次版本号与修订号都归零。
- 文档-only 改动按语义化版本本可以**不升版本号**；但本项目**例外**，理由见 §3 —— **只要上线就升**（至少升修订号）。
- 不为「凑数」而升版本号：合并提交、格式化、重命名等不影响产物的改动不需要单独升。

## 3. 产物文件名、缓存与版本号的关系（关键）

**当前状态（2026-10-12 起）**：构建输出**带内容哈希**的产物名，例如 `assets/index-DsGNGShv.js`、`assets/index-CWKVhQgF.css`（Vite 默认行为），且构建会清空输出目录。

由此得到两条结论：

1. **发版后线上 JS 的 URL 会变化** → 浏览器与 CDN 会自然去取新文件，不会让老用户停在旧代码上。
2. **版本号不再是「线上版本的唯一标识」**，但它仍是**人类可读的发布标识** —— `CHANGELOG.md` 的分节、以及「这次合并对应哪个版本」的对应关系都依赖它。

**因此：每次上线仍然必须升版本号。** 不是因为技术上需要它来区分文件，而是因为一旦不升，`CHANGELOG.md` 就失去了与线上版本的对应关系，出问题时无法快速回答「线上跑的是哪一版、那一版改了什么」。

> **历史与防回退（重要留档）**
> 2026-10-12 之前，本项目因一次关于本机构建环境的**误判**，把产物名固定为 `assets/index.js`（无内容哈希）并关闭了输出目录清空，造成两个后果：
> - 后果 A：发版后 JS 的 URL 不变 → CDN 长缓存会让老用户一直跑旧代码，「修复看起来没生效」；
> - 后果 B：`dist/` 里的上一版残留文件（例如两个版本的 `ai.worker-*.js`）会一起被上传。
>
> 该误判已被复测推翻（Vite 清空输出目录走的是内部文件系统操作，不经过 shell，与本机的 safe-delete 包装无关），并已修复。
> **若有人想把产物名改回固定名字、或重新关掉 `emptyOutDir`，请先读 `vite.config.ts` 里的注释** —— 那两条后果记录在那里，属「防回退」的一部分。

**唯一还依赖额外配置的环节是 `index.html`（以及 `/room/:id` 这类 SPA 路由入口）**：它引用着带哈希的 JS 文件名，所以它必须短缓存或不缓存，否则用户连新的 JS 引用都拿不到。该策略已在 `edgeone.json` 显式声明为响应头规则（2026-10-12），但**必须上线后实测是否真的生效**：方法与判据见 [`go-live-checklist.md`](go-live-checklist.md) 的「缓存行为确认」；策略全貌见 [`asset-cache-strategy.md`](asset-cache-strategy.md)。

## 4. 为什么不要轻易升主版本

本项目**前后端同域、同时发布**，看起来不存在「新代码配旧接口」的问题。但有一个现实缺口：

> **已经打开页面的玩家不会因为服务端发版而被强制刷新。** 他们手里仍跑着旧版 JS，直到自己刷新或缓存过期。

所以一次发版线上是**新旧混合**的：新部署的前端 + 旧标签页里的前端，同时打向同一套后端接口。推论：

- 接口必须保持**向后兼容**（只加字段、不改语义、不删字段），否则会打断正在对局的玩家 —— 这是「次版本号」的纪律。
- 真要升主版本，前提是**服务端能同时接受新旧两套请求**；做不到就必须缩短前端缓存，让旧标签页尽快失效。
- 这一条同样解释了为什么 `1.1.0` 定成次版本而不是主版本：棋谱字段是纯新增，旧客户端拿到多了字段的响应不会出错。

## 5. 一次发布要做的动作（照抄即可）

1. **改版本号**：`package.json` 的 `version`。
2. **落 CHANGELOG**：把 `CHANGELOG.md` 里 `Unreleased` 的内容移到新版本号条目下，写发布日期（用 `YYYY-MM-DD`）；确认「未发布」标记已去掉。
3. **跑自动化基线**：`npm run typecheck && npm test && npm run test:e2e` 三道全绿。
4. **确认构建产物带哈希**：`npm run build && ls dist/assets/` —— 应看到 `index-<hash>.js` / `index-<hash>.css`，且没有上一版残留。
5. **提交并合并**到部署分支（`main`）—— 平台会自动构建发布，**无需人工部署步骤**。
6. **按 [`go-live-checklist.md`](go-live-checklist.md) 走一遍**（合并前本机可确认的项 + 合并后真实环境自查的项）。
7. **核对一致性**（30 秒）：`package.json` 的 `version`、`CHANGELOG.md` 最新条目的版本号、你的预期发布版本，三者必须是同一个数。

> 只做 1–5 而跳过 6，等于「发出去了但不知道有没有生效」。
