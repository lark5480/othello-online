# ADR-0002：KV 无事务 → 乐观并发控制（`currentTurn` + `expectedUpdatedAt`）而非关系型数据库

- **状态**：已采纳（Accepted）
- **日期**：2026-09
- **决策者**：技术负责人
- **相关代码**：`edge-functions/lib/kv.ts`、`edge-functions/api/room/[roomId]/move.ts:40-53`、`src/pages/Room.tsx:44-49`

---

## 背景

一个黑白棋房间的全部状态（8×8 棋盘、双方 playerId、回合、步数、最后落子、胜负）必须持久化，且**每一步落子都是一次 read-modify-write**：

```
读 KV → 校验（回合归属 / 落子合法性）→ 内存中应用落子 → 写回 KV
```

这个 read-modify-write 若发生交错，后写者会**静默覆盖**先写者的合法落子。典型触发场景：

1. **重复提交**：玩家双击 / 网络重试，同一步落子发两次
2. **双方同时落子**：白方看到的是黑方落子前的状态，白方基于旧状态落子并写入
3. **轮询竞态**：客户端基于 2 s 前拉到的旧 `state` 发落子（`Room.tsx:104-108` 的轮询与 `:126-148` 的落子是两条独立路径）

**场景 3 是本作最可能的真实触发路径**，因为轮询间隔（2 s）与人类思考时间可能重叠。

同时，存储选型已被项目背景锁定：EdgeOne Makers 平台 + KV 绑定。KV 提供了 get/put/delete 与 TTL，**不提供事务、不提供 compare-and-swap、不提供原子自增**（`edge-functions/types.ts:6-10` 手写声明了平台注入的最小接口，只有这三个方法）。

因此问题不是「要不要用数据库」，而是「**在没有事务的存储上，如何保证对局状态不被错误覆盖**」。

## 决策

**采用乐观并发控制（Optimistic Concurrency Control）：不做写前加锁，而是在状态中维护单调递增的版本戳，写入前校验版本，写冲突则拒绝并让客户端拉取最新后重试。**

具体机制（三部分，缺一不可）：

### 1. 状态携带版本戳 `updatedAt`

`gameLogic.ts:40` 的 `GameState` 含 `updatedAt: number`。所有状态变更函数**无条件**把它设为 `now`：
- `createInitialState`（`:212,224`）—— `createdAt` 与 `updatedAt` 同值
- `joinState`（`:229,235`）
- `applyMoveToState`（`:252,302`）
- `restartState`（`:317,326`）

**「无条件」是刻意的** —— 不依赖调用方记得更新，因此不可能漏掉。

### 2. 服务端：写前校验版本

`move.ts:43-48`：

```ts
if (
  typeof expectedUpdatedAt === 'number' &&
  state.updatedAt !== expectedUpdatedAt
) {
  return error('state conflict', 409);
}
```

其上注释（`:40-42`）记录了决策理由：「客户端基于其看到的旧状态落子，若服务端状态已变化（对手已落子 / 重复提交），拒绝本次写入并让客户端拉取最新后重试，**避免一步合法落子在 read-modify-write 中被静默覆盖**」。

**关键点：校验发生在 `putState` 之前**（`move.ts:50-53` 的顺序是 `getState` → 校验版本 → `applyMoveToState` → `putState`），所以冲突的写入**根本不会落盘**。

### 3. 客户端：传版本 + 冲突后重拉

- `api.ts:63-76` 的 `postMove` 把 `expectedUpdatedAt` 放进 body
- `Room.tsx:131` 落子时带上 `state.updatedAt`（客户端当前所见状态的版本）
- `Room.tsx:134-141` 收到 409/400 时，重新 `getRoomState` 并 `applyState`，由用户重新落子

### 4. 客户端：读侧的陈旧数据过滤

`Room.tsx:44-49` 的 `applyState` 用 `lastAt` ref 过滤陈旧状态：

```ts
if (s.updatedAt >= lastAt.current) {
  lastAt.current = s.updatedAt;
  setState(s);
}
```

`Room.tsx:43` 注释明确了动机：「**通过 updatedAt 过滤 KV 最终一致性带来的陈旧数据**」。这一条与乐观并发**互补**：乐观并发防「写覆盖」，读过滤防「陈旧读把 UI 倒退」。

### 5. 存储层的次级防线：TTL

`kv.ts:16` `ROOM_TTL_SECONDS = 60*60*24`（24 h），`kv.ts:42-51` 的 `putState` 每次写入都带 `expirationTtl`（注释 `:47` 说明 `expirationTtl` 是平台选项，命名兼容 Cloudflare KV）。`kv.ts:12-14` 注释：「每次写入都会刷新该 TTL，因此进行中的对局不会过期」—— 这避免了长期挂起的房间无限占用存储。**TTL 每次写入刷新这一点需平台确认（见 §验证）。**

## 后果

**正面**：

- **零额外基础设施**。不需要数据库、不需要连接池、不需要迁移脚本。整个后端就是「一个 KV 绑定 + 5 个 handler」。
- **正确性覆盖了主要竞态**。重复提交（`expectedUpdatedAt` 已变 → 409）、双方同时落子（后到者的 `expectedUpdatedAt` 落后 → 409）、轮询竞态（同上）三条路径都被同一机制拦住。
- **冲突是可恢复的、且恢复路径已实现**（`Room.tsx:134-141` 自动重拉）。用户体验是「棋盘刷新一下，请重新落子」，而非「落子丢失且无提示」。
- **版本戳由状态转移函数无条件维护**，不依赖调用方自觉，从结构上排除了「漏更新版本」这类 bug。
- **读侧有独立防线**（`applyState` 的 `>=` 过滤），使 UI 不会因最终一致性倒退。

**负面 / 代价**：

1. **OCC 无法防住「相同毫秒内的两次写入」。** `updatedAt = Date.now()`（`gameLogic.ts:212` 等处的默认参数）是**毫秒精度**。若两次写入落在同一毫秒，`updatedAt` 相等，第二次的校验会**通过**，覆盖仍然发生。实际概率极低（需要两次 read-modify-write 在 1 ms 内完成网络往返到同一个 KV），但**这是一个已知的、理论存在的漏洞**。修法是改用单调递增计数器（`state.version += 1` 而非时间戳），成本约 5 行。**建议记入技术债，本轮不改** —— 时间戳已足够，且改为计数器会与 `applyState` 的过滤逻辑耦合。
2. **OCC 检测到的是「状态变了」，不是「我这一步是否已被应用」。** 场景 1（重复提交）中的第二次提交会得到 409，客户端重拉后发现棋盘上已有自己那一步 → `moveCount` 正确，UI 正常。**行为可接受，但客户端没有「幂等键」级的语义**，纯粹靠状态收敛。
3. **冲突时用户需重新落子。** 不是最优体验（理想是服务端识别「你要落的这一步在最新状态上仍合法」并自动重放）。但当前场景 3 的冲突意味着对手已经落子，用户的原落子**大概率已经不合法的**，重放本身也不可行。**判定：当前设计是对的。**
4. **乐观并发只加在 `move` 上，未覆盖 `join` 与 `restart`。**
   - `join.ts:36-40`：白方空位才加入，两个并发 join 可能都看到「白方空位」→ 都写入 → 后者覆盖前者，**先到的玩家被踢出且不知情**。真实触发路径：同一个房间码被两个人几乎同时输入（可能是一方把码分享给了第三方）。
   - `restart.ts:39-40`：无版本校验，但 `restart.ts:26-28` 已限定「仅 `status === 'finished'`」，且 `restartState` 是幂等的全量重置（`:317-328`），**覆盖风险低**。
   - **判定**：`join` 的竞态是真实的低危缺陷。修法是 join 也带 `expectedUpdatedAt`。**建议记入技术债。**
5. **`applyState` 的 `>=` 而非 `>`**（`Room.tsx:45`）：这意味着**同版本的状态被再次应用**（例如用户手动点「刷新状态」，`Room.tsx:360-365`）会导致一次多余的重渲染与一次 `useBoardSound` effect 执行。`useBoardSound` 内部用 `moveCount` 比较（`useBoardSound.ts:51`）不会重复播音。**影响可忽略。**

## 替代方案

| 方案 | 为何未采纳 |
|---|---|
| **A. 换成关系型数据库（带事务 / 行锁 / CAS）** | 需要额外的数据库服务、连接管理、凭据、迁移与部署步骤。对一个「两人对局、每步一次写」的负载，**复杂度与收益严重不成比例**，且与项目已锁定的 EdgeOne + KV 部署形态（`edgeone.json`、`kv.ts:18-23` 注释明说「自托管时可在此替换为其他可达的存储实现」，即已预留扩展点但当前不需要）冲突。**否决。** |
| **B. 悲观锁（写前 `put` 一个锁键 / 用 KV delete 做互斥）** | KV 无原子 test-and-set：读锁 → 写锁之间仍有窗口，反而引入「锁泄漏导致房间永久卡死」的新故障模式。且需要额外的超时与解锁路径。**否决。** |
| **C. 不做并发控制，靠「客户端自律」** | 即依赖 2 s 轮询恰好不与落子重叠。这是把正确性寄托在时序巧合上，**任何网络抖动、重试、用户双击都会打破**。`usePolling.ts:38-43` 的串行循环只保证「单客户端不堆积请求」，完全不保证跨客户端的落子互斥。**否决。** |
| **D. 每次落子写入一条独立的 move 日志，只存「最新快照」由日志推导** | 需要列表查询能力（`kv.ts` 的接口只有 get/put/delete，无 list），且读取时需重放全量日志 —— 读取成本随步数线性增长，把每步 O(1) 的读取变成 O(n)。对 60 步的对局是可接受的，但复杂度明显更高且无对应收益。**否决。** |
| **E. 用 KV 的 `expirationTtl` 做乐观锁载体（短 TTL 抢占）** | 把 TTL 当锁语义是滥用；且无法表达「我基于哪个版本」。**否决。** |

## 验证与失效条件

**已验证（自动化）**：
- `edge-functions/flow.test.ts`（211 行）覆盖完整对局流程；`edge-functions/router.test.ts`（128 行）覆盖路由分派
- `src/pages/Room.test.tsx:Room 落子与冲突重试 > 我方回合可落子：点击合法格调用 postMove 并携带回合版本` —— 明确断言 `postMove` 收到了回合版本
- `npm test` 本机实测：**14 个测试文件 / 126 个用例全部通过**（2026-10-12，Node v22.22.2）

**必须人工验证（不联网无法判定，见 `asset-audit.md` §4）**：
- **V1（最关键）**：EdgeOne KV 的真实一致性模型。若 KV 是**强一致**的，本 ADR 的 OCC 机制是「防御性但非必需」的；若 KV 是**最终一致**的（Cloudflare KV 即典型），则 OCC 是必需的，且 `expectedUpdatedAt` 校验窗口可能不足 —— 因为存在「A 读到旧值 → B 写入新值 → A 基于旧值写入」的窗口，而 OCC 恰好**能**检出（A 的 `expectedUpdatedAt` 是旧值，与 B 写入的新值不等）→ 409。**结论：OCC 在最终一致的 KV 上同样有效，这是本决策的关键正确性依据。**
- V6：`expirationTtl` 是否每次写入刷新（`kv.ts:12-14` 的注释假设）。

**失效条件（应重新评估本决策）**：
1. 状态写入不再由 `gameLogic.ts` 的四个状态转移函数统一产生（则 `updatedAt` 无条件维护的保证消失）
2. 需要在同一房间内并发落子（当前是严格回合制，`gameLogic.ts:254-260` 强制 `status === 'playing'` 且校验回合归属 → **天然把并发窗口压到极小**；这是 OCC 之所以够用的隐含前提）
