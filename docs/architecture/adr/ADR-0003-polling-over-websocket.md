# ADR-0003：用 HTTP 轮询而非 WebSocket / SSE 做联机同步

- **状态**：已采纳（Accepted）
- **日期**：2026-09
- **决策者**：技术负责人
- **相关代码**：`src/hooks/usePolling.ts`（53 行）、`src/pages/Room.tsx:88-119`、`src/utils/api.ts`（88 行）

---

## 背景

联机对弈需要一个**双向状态同步通道**：我的落子要让对方看到，对方的落子要让我看到。

这是本作最核心的实时性需求，方案的取舍直接决定「落子 → 对方可见」的延迟量级。

约束背景：

1. **后端形态已被锁定**。项目部署在 EdgeOne Makers，运行时为 **Edge Functions（V8 isolate）**（`edge-functions/types.ts:1-4`：「真实类型由 EdgeOne 平台在运行时注入」）。**Isolate 模型的关键特性是「有请求才执行」** —— 没有常驻进程，因此没有进程内可以保持的 WebSocket 连接。
2. **存储是 KV**（`kv.ts:24-26` 的 `context.env.OTHELLO_KV`），无变更订阅能力、无 pub/sub。
3. **状态体积极小**：`toPublicState` 后的一个 `GameState` 是一个 8×8 的 `number[][]` 加几个标量（`gameLogic.ts:27-41`），JSON 序列化后约 300–500 B 量级（**估算，未实测具体字节数**）。
4. **游戏节奏慢**：一局 60 步，人类每步思考数秒到数十秒。**实时性需求是「秒级」而非「毫秒级」。**

## 决策

**用 HTTP `GET /state` 轮询拉取状态，落子走 HTTP `POST`。不引入 WebSocket、SSE、或任何长连接。**

具体设计：

### 1. 全部通信是四个普通 fetch

`api.ts:33-88` 定义的四个请求，全部是 `fetch` + JSON：
- `createRoom` → `POST /api/room/create`
- `joinRoom` → `POST /api/room/:roomId/join`
- `getRoomState` → `GET /api/room/:roomId/state`（**唯一的轮询端点**）
- `postMove` → `POST /api/room/:roomId/move`
- `restartRoom` → `POST /api/room/:roomId/restart`

### 2. 轮询间隔按状态自适应

`Room.tsx:88-102` 是核心决策表：

| 对局状态 | 是否轮询 | 间隔 | 理由（源码注释/代码结构） |
|---|---|---|---|
| `waiting`（等对方加入） | ✅ 轮询 | 3 s | 对方加入是低频事件；`usePolling.ts:11-12` 注释「自己回合时传 `enabled=false` 即可停止轮询」 |
| `playing` · 自己回合 | ❌ **停止轮询** | — | `pollEnabled = !myTurn`。**这是最重要的优化** —— 我不需要知道任何变化，因为只有我能落子 |
| `playing` · 等待对方 | ✅ 轮询 | **2 s** | 延迟的主要来源（见下） |
| `finished` | ✅ 轮询 | 5 s | `Room.tsx:98` 注释：「对手点『再来一局』后本端自动恢复，无需手动刷新」 |

### 3. 串行循环，而非固定 interval

`usePolling.ts:33-50`：

```ts
const loop = async () => {
  if (cancelled) return;
  await refresh();           // 等本次请求完成
  if (cancelled) return;
  timer = setTimeout(loop, intervalMs);   // 完成后再排下一轮
};
loop();
```

**这是串行链式调度，不是 `setInterval`。** 慢响应不会导致请求堆积（不会出现「上一轮还没回来就发下一轮」）。`usePolling.ts:37` 的 `cancelled` 标志 + `:46-49` 的 cleanup 避免了组件卸载后的 setState 与定时器泄漏。

### 4. 落子走「先写后拉」，不等轮询

`Room.tsx:131-132`：`postMove` 的响应**直接包含新状态**（`move.ts:54` 返回 `{state: toPublicState(res.state)}`），落子方不需要等下一次轮询就能看到自己的落子。这是关键的延迟优化 —— **自己落子的 UI 更新是网络 RTT 量级（几十 ms），不是轮询周期量级（2 s）。**

### 5. 冲突恢复内置

`Room.tsx:134-141`：409/400 时自动重拉最新状态（配合 ADR-0002 的 OCC）。

### 6. 明确的降级路径

`api.ts:14-23` + `api.ts:18-19` 的 `STORAGE_HINT`：当 KV 未绑定时，后端返回 503 `storage not configured`（`kv.ts:9`），前端识别后展示友好提示，引导用户改玩人机对战。**这个降级路径的存在本身就要求同步层不能有额外的、长连接的资源依赖。**

## 后果

**正面**：

- **与部署形态完全契合**。Edge Functions 无常驻进程，轮询是「有请求才执行」模型下的自然形态。不需要为长连接做任何平台适配或付费升级。
- **状态同步的正确性简单**。每次 `GET /state` 都是一次完整的、无缓存的快照拉取（`http.ts:8` 统一 `Cache-Control: no-store`），**不存在消息丢失、乱序、增量状态漂移**这类别名系统的问题。陈旧数据由 `Room.tsx:44-49` 的 `updatedAt` 过滤兜住。
- **「自己回合停轮询」把平均请求量降到约 0.5 req/s/客户端的一半以下**。一局 60 步中，每个客户端约有 30 步在等待对方（需轮询）、30 步轮到自己（不轮询）。
- **断线重连天然免费**。网络断开恢复后，下一次轮询自动拿到最新状态，不需要额外的重连逻辑（对比 WebSocket 需要重连握手、心跳、状态重放）。
- **零额外依赖**。WebSocket 方案在浏览器端虽可用（原生 API），但服务端侧需要长连接支持 —— 这恰恰是 Edge Functions 缺的，也是本决策的**决定性理由**。
- **实现极简**。`usePolling.ts` 只有 53 行，全部逻辑（串行调度、取消、错误捕获）都在这一个文件里，无隐藏状态。

**负面 / 代价**：

1. **「落子 → 对方可见」延迟上界 = 轮询间隔 + RTT = 2 s + 网络往返。**
   这是本决策最重要的量化代价。实测无法在本地验证（见下），预算设为 ≤ 2.4 s P95（`performance-budget.md` B6）。
   **缓解**：`Room.tsx:88-102` 的自适应间隔已把等待方的间隔压到 2 s；且这是**上限**而非典型值 —— 平均约 1 s（RTT 与轮询相位随机）。
2. **请求量随人数线性增长**。N 个客户端 → 0.5N req/s。对小规模（朋友间对战）完全可接受；对大规模则不可行。**判定：本场景定位下可接受。**
3. **存在「理论上的可见性延迟」导致的操作困惑**。白方落子后，黑方可能在自己的下一次轮询前（约 2 s 内）看到旧棋盘并尝试落子 → 服务端返回 409 not your turn（`gameLogic.ts:258-260`）→ 客户端重拉（`Room.tsx:134-141`）。**体验是「点了没反应，然后棋盘刷新」**。可接受，但**非最优** —— 最优是落子时做本地前置检查。
   **建议的改进（未实施）**：非我方回合时把棋盘格子设为 `disabled`（当前 `Room.tsx:280` 的 `interactive={!!myTurn}` 已实现，即棋盘**已经**不可点；因此这条实际上已被处理）。**降级为无问题。**
4. **无「对方正在思考」的在途信号**。UI 只能显示「等待对方落子…」（`GameInfo.tsx:37`），无法区分「对方在想」与「对方已断线」。**低危，可接受。**
5. **未做请求去抖/抖动**。多个客户端（尤其同一局域网多人测试时）会以固定 2 s 频率同频打点，可能在服务端形成周期性尖峰。**建议**：给间隔加 ±20% 抖动（低成本），记入技术债。
6. **轮询请求的幂等性**。`GET /state` 天然幂等，无问题。✅

## 替代方案

| 方案 | 为何未采纳 |
|---|---|
| **A. WebSocket** | **决定性否决理由**：Edge Functions 是无状态的 V8 isolate（`types.ts:1-4`），没有常驻进程来持有长连接。WebSocket 需要一个常驻服务器（Cloudflare Durable Objects / 独立 WS 服务 / SSE 网关），意味着**引入项目当前刻意不依赖的常驻基础设施**。同时需要自己实现心跳、重连、消息重放、状态同步 —— 而当前同步需求只是「拉一个 400 B 的快照」。成本与收益严重不成比例。**否决。** |
| **B. SSE（Server-Sent Events）** | 比 WebSocket 轻，但**同样需要常驻进程**来维持连接。同样否决于 isolate 模型。**否决。** |
| **C. KV 轮询 + 更短间隔（如 500 ms）** | 可降低延迟上界，但请求量 ×4（2 req/s/客户端）。且 `kv.ts` 接口只有 get/put/delete，**高频轮询会显著推高 KV 读配额与成本**。**当前 2 s 是延迟与成本的合理平衡点。否决，除非实测发现 2 s 的体验不可接受（需 V2 验证）。** |
| **D. 落子用 WebSocket 推送 + 轮询兜底（混合）** | 复杂度翻倍，且仍需常驻进程。**否决。** |
| **E. 长轮询（long-polling：服务端挂起直到状态变化）** | 技术上更贴合（低延迟 + 无长连接），但要求服务端**挂起一个 isolate 直到状态变化** —— 在无订阅能力的 KV 上，服务端只能自己轮询 KV，即「服务端在轮询」，请求量不降反升，且挂起时长受 isolate 超时限制。**否决。** |
| **F. 第三方实时服务（Pusher / Supabase Realtime / 自建 WebSocket 网关）** | 引入外部运行时依赖（违反零运行时依赖约束，见 `asset-audit.md` §1.1）与新的鉴权面（需要 API key）。对两个玩家、每步一次的场景，成本明显过高。**否决。** |
| **G. 保持轮询，但缩短到 1 s** | 请求量翻倍到 1 req/s。**若 V2 人工验证发现 2 s 体验不佳，这是首选调参方案**（改 `Room.tsx:96` 一个数字）。记为备选预案。 |

## 验证与失效条件

**已验证（自动化）**：
- `src/hooks/usePolling.test.ts`（6 个用例）覆盖 `usePolling` 的行为
- `edge-functions/flow.test.ts`（211 行）+ `router.test.ts`（128 行）覆盖端点
- `npm test` 本机实测：14 文件 / 126 用例全通过（2026-10-12）

**必须人工验证**：
- **V2（最关键）**：真实部署下的「落子 → 对方可见」延迟 P50/P95。预算 ≤ 2.4 s（`performance-budget.md` B6）。若 P95 超过 4 s，触发替代方案 G（间隔 2 s → 1 s）。
- V1：KV 读延迟与一致性。若 KV 读本身有数百 ms 的传播延迟，2 s 间隔的必要性会上升。

**失效条件（应重新评估本决策）**：
1. **引入常驻服务器**（如 Cloudflare Durable Objects 或任何长进程后端）—— WebSocket 立刻变得可行且更优
2. 对局需要亚秒级同步（如实时竞技对抗）—— 本作是回合制慢节奏棋类，**不满足**
3. 单房间并发人数达到数十量级 —— 0.5N req/s 的线性增长会成为瓶颈
4. 需要「对方正在思考 / 已断线」的在途信号 —— 需引入额外的在线状态通道
