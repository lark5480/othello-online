## 🛡 回归防线（每个修掉的 Bug 都必须填）

> **为什么单独一节**：没有自动化断言的 Bug 一定会回归。
> 「手动确认过了」不是防线——下一个人改代码时不会重跑你的手动步骤。
> 这一节的唯一目的：**让这个 Bug 永远不再回来。**

### 1. 必须留一条自动化断言

| 项 | 填什么 |
|---|---|
| 断言放在哪 | `e2e/*.spec.ts`（端到端链路） / `src/**/*.test.ts`（逻辑层） |
| 断言内容 | <!-- 用一句话写清"断言什么等于什么"，例：刷新后走子记录仍为 2 手 --><br><!-- 关键：要断言**具体事实**，不是"没报错" --><br>如 `await expect.poll(() => moveCount(pageA)).toBe(2);` |
| 为什么断言在这里 | <!-- 说明它覆盖的是哪一层：UI / 状态派生 / 持久化 --><br><!-- 经验：断言要打在**根因那一层**，不是打在表现层。--><br><!-- 例：BUG-01 根因是状态模型缺字段，断言就应验证持久化后的完整数据，--><br><!--     而不是只验证"侧栏看起来有东西" --><br> |

### 2. 如果原先用 `test.fail()` 标注（Playwright「预期失败」）

> ⚠️ **这是最容易翻车的一步。**「预期失败」标记的是"现在应该是坏的"。

- [ ] 修复 PR **已移除** `test.fail()` 标注
- [ ] 断言**保留**（它就是回归防线，**不要连测试一起删**）
- [ ] 已在 PR 描述里写明"移除 test.fail 标注"，避免 reviewer 误判为"删测试"

> **不移除会怎样**：Bug 修好了，用例转为 `unexpectedly passed` → **套件变红**。
> 结果是「明明修好了，CI 却挂了」，很容易被误判成修复失败而回滚。

### 3. 填`smoke-checklist.md` 的对应条目

- [ ] 已在 `tests/playtest/smoke-checklist.md` **对应分组补/改条目**
- [ ] 覆盖方标记为 `[E2E·xxx]` / `[UNIT]`
- [ ] 若**修复前该用例是失败的**，在条目上注明（例：`⚠️ 修复前失败，见 reconnect-BUG-01`）

> 这样后人看清单时，能分清"这条一直有覆盖"和"这条是后来补的"。

### 4. 自检三问

- [ ] 如果有人把修复代码删掉，这条断言会**失败**吗？（不会 → 断言写得没到位）
- [ ] 如果有人把修复代码改回旧写法（绕过而非修复），这条断言会**失败**吗？
- [ ] 这条断言测的是**根因**，还是只是**现象**？只测现象 → 根因回归时可能测不出来

## 真实案例参考（本项目已发生，建议照此办理）

### `reconnect-BUG-01` · 断线刷新后走子记录退化为「1 手」

| 项 | 内容 |
|---|---|
| 现象 | 落子 2 手显示「2 手」→ F5 刷新 → 变「1 手」，第 1 手永久丢失；「回顾」重放出错误棋形 |
| 根因 | `GameState` 只有 `moveCount` + `lastMove`，**从不持久化每手坐标**；`MoveHistory` 的 `entries` 是纯 `useState`，靠增量差分追加，刷新后归零 |
| 为何漏掉 | 刷新前显示正确**不是因为逻辑对，而是因为增量差分恰好连续**——典型的"碰巧对"实现 |
| 分级 | **P2**（已定级，主理人确认）。棋盘/计分/胜负不受影响，属展示层数据丢失；按 P0 字面执行会造成 P0 通胀。见 `phase6-verdict.md` 5.4 |
| 发现方式 | **自动化 E2E**，非真人试玩——试玩本轮根本没执行 |
| 防线 | `e2e/reconnect.spec.ts` BUG-01 用例 + `smoke-checklist.md` 的 **C7** |
| ⚠️ 交付注意 | 修复落地时**必须移除 `test.fail()` 标注**（见上节第2 条） |

> **这条 Bug 的两条通用教训**：
> 1. **断言要打在根因那一层**（持久化的完整数据），不要只打表现层（侧栏有内容）。
> 2. **"碰巧对"的实现要主动测破坏路径**——正常流程走通不等于逻辑正确。
>    BUG-01 正是靠"刷新"这个破坏路径才暴露的。

## 分级标准（照这个判，别凭感觉抬级）

### ⚖️ 分级的正确顺序（先看这条）

> **别直接套条款——先问后果，再选级别。**

| 步骤 | 动作 | 作用 |
|---|---|---|
| **1 · 定锚** | 问「**这局还能不能信？**」（棋盘/计分/胜负/回合是否可信） | 定**上限**：不可信 → 最高 P0；可信 → 进不了 P0 |
| **2 · 校准** | 用下面条款对照，**在上限内**取最贴切的一级 | 定**具体级别** |

**为什么不能直接套条款**：条款是枚举式的，必然出现「字面命中、实际危害不足」的情况。
此时**可以下调，但必须注明主理人确认**（见下方「下调规则」）。
否则 P0 会通胀——**一旦 P0 反复出现，真 P0 就失去警示意义了**。

> **一句话**：**先看后果定上限，再用条款选级别。**

### 🔴 严重级 / P0 —— 零容忍，本轮必修

游戏**不能正确进行**或**数据不可信**。出现任意一条即为 P0：

1. **落子丢子**：落了子但棋盘没变 / 刷新后棋子消失 / 双方看到不同的棋盘。
2. **对局卡死**：非终局状态双方都无法落子，且没有任何"跳过/结束"提示，只能靠刷新恢复。
3. **身份错乱**：刷新或重连后黑白方身份变了 / 双方都认为该自己走。
4. **状态不同步且不自愈**：双方回合提示永久冲突，且不会自动收敛。
5. **终局算错**：终局比分与棋盘实际棋子数不符；或只有一方进入终局；或该结束的局卡在中间。
6. **重复落子被接受 / 非法落子被接受**（规则引擎被绕过）。
7. **数据永久丢失**：重开局后走子记录/战绩被清空且非预期。

> 判断口诀：**这局还能不能信？** 不能信 → P0。
> 这类 Bug 出现一次，Phase 6 就不能算过。

#### 下调规则（字面符合但实际影响不足时）

**可以下调一级**，但必须同时满足：

- [ ] 已确认「**这局还能不能信**」——棋盘/计分/胜负/回合**全部可信**，玩家能正常下完并得到正确结果
- [ ] 已写明「**字面符合哪条，实际影响不足在哪**」
- [ ] 已注明「**主理人确认**」——下调是**产品侧的容忍度决策**，QA 不能单方面定
- [ ] 属于「字面符合但危害不足」这**一种**情形，不是别的

**⚠️ 不得下调的情形**：

- 字面符合 P0 **且实际危害也足够**（真丢子、真卡死、终局算错）→ **按 P0 走，不许降**
- 拿不准时→ **按 P0 报**，让主理人决定降不降。**宁严勿松**

> **本项目先例**：`reconnect-BUG-01` 字面符合 P0 第 7 条「数据永久丢失」，
> 但棋盘/计分/胜负未受影响（这局仍可信），经主理人确认下调为 **P2**。
> 完整推理见 `phase6-verdict.md` 5.4 / 5.4.1。

### 🟠 A 级 / P1 —— 严重影响体验，本轮尽量修

游戏能玩通，但**明显难受或明显误导**：

1. **同步延迟可感知且无反馈**：落子后对方 > 10 秒才看到，且没有任何"等待同步"提示。
2. **刷新后需要额外操作才能继续**：没丢对局，但要重新进/重连一次才能落子。
3. **可发现性问题**：核心入口（人机对战 / 难度选择 / 提示开关）找不到，需要口头指导。
4. **无合法落子时跳过没有提示**，用户以为卡死。
5. **AI 思考时界面冻结** > 1 秒，或 AI 落子没有任何状态反馈（静默等待）。
6. **终局结算要素缺失**：比分对了但没有胜负文案 / 没有"再来一局"入口 / 结算不可见。
7. **难度梯度失效**：简单档新手打不过，或困难/大师赢面压倒性（> 90%）。
8. **可访问性硬伤**：键盘无法完成一次落子；焦点不可见；屏幕阅读器读不出当前回合。

### 🟡 B 级 / P2 —— 视觉/手感瑕疵，不阻断，下一轮修

1. 翻转动画太快/太慢、节奏突兀、"啪"一下没有过程感。
2. 暗色模式对比度不足：棋子与棋盘边界不清、提示点看不见、次要文字偏暗（**能读清就不算 bug，算偏好**）。
3. 提示点样式不显眼 / 有轻微闪烁。
4. 音效音色或音量不协调（不影响判定）。
5. 布局间距、圆角、字号细微不一致。
6. 走子历史滚动不顺/长列表性能下降。
7. 文案、错别字、术语不一致。
8. 战绩面板展示维度不直观。

### ⚪ 不算 Bug（记为"建议"）

- 觉得"应该能悔棋" —— 悔棋 PRD 标 P2 未实现，属**功能缺失**不是缺陷，开 feature 单。
- 界面风格个人偏好。
- "AI 太强了" —— 属难度平衡，走 `observation-sheet.md` 的手感反馈给设计侧。
