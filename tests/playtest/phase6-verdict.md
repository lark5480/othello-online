自动化能证明"刷新后数据一致"，**证明不了**：

既无单测，也无 n=1 记录。若线上用户开着暗色，**棋盘可读性是未验证风险**。

翻转动画的"爽感"、AI 落子的节奏感、音效的舒适度——n=1 给了"不刺耳/不卡"的**弱结论**，但样本量为 1 且非独立用户。

### 3.4 上线环境（mock ≠ 线上）

`playwright.config.ts` 的 `webServer` 跑的是 `npm run dev` + 内存版 mockApi。
**EdgeOne 真实部署环境（真实 KV、真实网络延迟、真实并发）本轮零验证。** mock 通过 ≠ 线上通过。

## 五 ★ 本轮发现的真实 Bug：`reconnect-BUG-01`

> 这一节是本报告最有价值的部分。**这个 Bug 不是靠真人 Playtest 发现的**——
> 真人试玩根本没执行。它是被**自动化 E2E 撞出来的**，这一点需要单独讨论。

### 5.1 Bug 描述

**标题**：`[走子记录] 断线刷新后走子记录退化为「1 手」，历史手数永久丢失`

| 项 | 内容 |
|---|---|
| 复现率 | **必现（10/10）** |
| 触发条件 | 任意模式下刷新页面，且已落子 ≥ 2 手 |
| 分级 | **P2 / B 级**（详见 5.4） |
| 发现路径 | `e2e/reconnect.spec.ts`（本轮新增），非真人试玩 |

**现象**：A、B 交替落子 2 手 → 走子记录正确显示「2 手」→ A 按 F5 刷新 → 记录变成「1 手」，第 1 手永久消失。

### 5.2 根因（已独立复核，非转述）

我用静态核对独立确认了根因，**与 engineering-lead 的结论一致**：

```
① GameState（gameLogic.ts:27-41）
   只有 moveCount: number + lastMove: Move | null
   → 每手坐标从未被持久化，服务端无法把完整棋谱下发

② MoveHistory（MoveHistory.tsx:26-40）
   const [entries, setEntries] = useState<Entry[]>([])   ← 纯客户端状态
   useEffect：仅当 state.moveCount > prevCount.current 时 push 一条 state.lastMove

③ 刷新后：prevCount = 0，moveCount = 2，lastMove 只有最后一手
   → 条件成立 → 只 push 1 条 → 显示「1 手」
```

**关键判断**：刷新前能正确显示 2 手，**不是因为逻辑正确，而是因为增量差分恰好连续**。
这是一个"碰巧对"的实现——只要刷新就崩。这是典型的**隐性状态派生缺陷**。

### 5.3 影响面（划清边界，避免过度放大）

| 受影响 | 不受影响 |
|---|---|
| 走子记录条数错误（`{entries.length} 手`，MoveHistory.tsx:51） | 棋盘局面（走 `board` 真实数据） |
| 「点击回顾该手棋形」失真：`reconstruct`（:121-127）从初始盘重放残缺 entries，重放出**错误局面**，且回放起点与真实第 N 手不对应 | 计分与胜负判定（走 `board`） |
| 人机对战 / 本地双人模式**同样受影响**（MoveHistory 三处共用） | 回合流转、并发控制（走 `updatedAt` 乐观锁） |

> **定性关键**：这是**展示层数据丢失**，不是**对局数据不可信**。
> 玩家这局的胜负结果是对的。判P2而非 P0——依据见 5.4。

### 5.4 为什么是 P2 而不是 P0（分级依据 · 已定级）

> **最终分级：P2** —— **主理人已确认**，采信 QA 建议（2026-10-12）。本节结论已固化，不再是待议状态。

### 5.4.1 ★ 固化经验：分级的正确顺序（比单个 Bug 更有长期价值）

> 这条经验来自本次真实定级争议，**适用于此后每一个 Bug**，故单列。

**❌ 错误顺序：先套字面条款 → 再看影响**

会导致**分级通胀**：凡是沾了"数据丢失""状态不对"字样的都往 P0 塞。
后果是**真 P0 失去警示意义**——当 P0 反复出现，它就不再传递任何有效信号。

**✅ 正确顺序：先问「这局还能不能信？」→ 再用字面条款校准**

| 步骤 | 动作 | 作用 |
|---|---|---|
| **第 1 步 · 定锚** | 问一句「**这局还能不能信？**」<br>（棋盘 / 计分 / 胜负 / 回合是否可信） | 确定**上限**：不可信 → 最高只能 P0；可信 → 进不了 P0 |
| **第 2 步 · 校准** | 再用模板字面条款对照，**在上限内**取最贴切的一级 | 确定**具体级别**，避免凭感觉拍 |

**核心：字面条款用来在「不可信」这个上限内选级别，而不是用来决定"是不是 P0"。**

**为什么必须分两步**：

1. 模板条款是**枚举式**的，必然存在"字面命中但实际危害不足"的情况——BUG-01 就是典型。
2. 若允许字面条款直接定级，**P0 会通胀**；而 P0 的价值恰恰来自它的**稀缺性**。
3. 「这局还能不能信」是**后果导向**的，直接对应用户的真实损失，不受条款措辞影响。

> **一句话记忆**：**先看后果定上限，再用条款选级别。**

**适用边界（防止这条经验被滥用成降级借口）**：

- 若某 Bug **字面符合 P0 且实际危害也足够**（真丢子、真卡死、终局算错），**不得下调**，按 P0 走。
- 下调必须**注明主理人确认**——这是**产品侧的容忍度决策**，QA 不能单方面定。
- 本条**仅适用于**"字面符合但危害不足"这一种情形，不适用于其他任何情况。

### 5.5 发现路径的方法论结论 ★

**这个 Bug 揭示的核心事实：自动化 E2E 能顶什么、不能顶什么。**

| 维度 | 真人 Playtest | 自动化 E2E |
|---|---|---|
| 能否发现 BUG-01 | **不能**（试玩根本没执行） | **能，且已发现** |
| 发现方式 | — | 刷新前后**断言同一事实**（2 手），差分比对 |
| 适用条件 | 需要人、需要时间、需要被试 | 有状态断言 + 可重复 |
| 上限 | 能发现"人不舒服" | **只能发现"数据不对"** |

**三条方法论结论**：

1. **机器补强顶上了"数据正确性"这一块，且顶得很好。** T2 原本零覆盖，补上 E2E 后**立刻撞出真实 Bug**——证明"零覆盖"和"有覆盖"的差距不是形式主义。
2. **机器补强顶不上"体验正确性"。** 9 项零证据覆盖一项未少。E2E 证明了"刷新后棋盘/计分/执子色都对"，**证明不了**刷新回来的人**自己知不知道**已经回到对局、**觉不觉得**等待体感可接受。
3. **本轮的核心结论**：真人不可得时，机器补强**能守住 P0 底线**（数据不可信类问题），
   但**体验层只能降级为"未覆盖"**，不能因为机器测过了就当作没问题。

> 这也验证了我上一轮的判断——**T2 是最高风险路径**。它不仅有风险，而且**真的出问题了**。
> 如果当初没补这层 E2E，BUG-01 会带着"零证据"状态进入线上。
